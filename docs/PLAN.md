## 1. Technik-Stack

Grundsatz (N7): Jede Bibliothek muss begründet sein. Was sich mit wenig eigenem Code lösen lässt, wird selbst geschrieben.

Abhängigkeiten gesamt: 11. Laufzeit: `preact`, `lucide-preact`, `@fontsource-variable/archivo`, `uqr`. Entwicklung: `typescript`, `vite`, `vitest`, `@vitest/coverage-v8`, `@playwright/test`, `@axe-core/playwright`, `@biomejs/biome`.

Einrichten: `npm run setup` (`scripts/setup.mjs`) führt `npm install` und `npx playwright install chromium webkit` aus. `npm run check` prüft vorab, ob die Browser vorhanden sind, und verweist sonst auf `setup`.

Schritte von `npm run check`:
1. `biome check` (lokal mit `--write`, in CI nur prüfen)
2. `tsc --noEmit`
3. `vitest run --coverage` (schlägt fehl, wenn keine Tests gefunden werden oder die Abdeckung unter 90 % liegt)
4. `vite build`
5. `playwright test` (4 Projekte: chromium-desktop, chromium-mobile, webkit-desktop, webkit-mobile)

## 3. Leitlinien für den Code

- Keine echten Personennamen in Code, Tests oder Beispieldaten. Personen sind intern `personA`/`personB`; Namen stehen in den Einstellungen. Zuständigkeit: `personA | personB | both`.
- Fachlogik in `src/domain/` kennt weder DOM noch Speicher; sie bekommt „heute“ als Parameter.
- Jedes Akzeptanzkriterium aus ANFORDERUNGEN.md ist mindestens ein Test, benannt nach dem Kriterium.
- Exportformat und gespeicherte Daten tragen eine `schemaVersion`.
- Eine Aufgabe pro Sitzung (T2); vor Fragen an Claude erst `npm run check` (T3).
- Oberfläche nach `docs/design/DESIGN.md`: nur Tokens aus `src/ui/tokens.css`, keine festen Farben; jede neue Farbkombination kommt in `src/ui/tokens.test.ts`. Neue Seiten und Dialoge prüft axe automatisch in beiden Farbschemata.

## 5. Umsetzung Paket 7 (Entscheidungen)

- **Bildschirme:** Die App lädt Daten und Gerät und zeigt dann genau einen von fünf Zuständen: Laden, Speicherproblem, Ersteinrichtung (keine Namen), „Wer benutzt dieses Gerät?“ (Namen da, „Ich bin“ fehlt, z. B. neues Gerät), eigentliche App mit Navigation. Die Ersteinrichtung fragt Namen **und** „Ich bin“ in einem Schritt; dasselbe Formular steht unter „Einstellungen“.
- **Namen (`checkPersonNames`, Fachlogik):** getrimmt, nicht leer, höchstens 30 Zeichen, beide verschieden (ohne Rücksicht auf Groß-/Kleinschreibung).
- **Fokusführung:** Jede Seite hat genau eine `h1` (`PageTitle`); beim Seitenwechsel setzt sie den Tab-Titel („Seite – Putzplan“) und nimmt den Fokus. Beim ersten Laden nicht, damit „Zum Inhalt springen“ der erste Tabulator-Stopp bleibt. „Zum Inhalt springen“ ist ein Button, kein `#inhalt`-Link, weil das den Hash-Router auslösen würde.
- **Unlesbare Daten:** `AppStorage.loadRaw()` liefert den gespeicherten Text unverändert, `discard()` löscht ihn. Die App zeigt die Meldung mit Fundstellen; Weg 1 lädt `putzplan-rohdaten-JJJJ-MM-TT.json` herunter; erst danach erscheint Weg 2 „Neu beginnen …“, der eine Rückfrage (`<dialog>`, Fokus zuerst auf „Abbrechen“) stellt. Ist der Browser-Speicher selbst gesperrt (auch schon der Zugriff auf `localStorage` wirft), gibt es keine Rohdaten und kein Löschen, nur „Erneut versuchen“. „Ich bin“ des Geräts bleibt beim Verwerfen erhalten.
- **Platzhalter:** Woche, Aufgaben und Erledigt zeigten „Diese Seite ist noch im Aufbau.“ bis zu den Paketen 8–11. Seit Paket 11 gibt es keine Platzhalter mehr (`PlaceholderPage` ist entfernt).
- **Veröffentlichung:** `.github/workflows/pages.yml` läuft nach erfolgreichem Workflow `check` auf `main` und veröffentlicht den Build (`dist`) über GitHub Pages; manuell startbar. Pages-Quelle „GitHub Actions“ muss einmalig im Repository aktiviert sein.
- **Neue Abhängigkeit:** `@kern-ux/native` (war im Stack vorgesehen, siehe Tabelle oben). Nur CSS und Fira Sans werden eingebunden, nicht die Kopfzeile (Bundesflagge) und kein KERN-JavaScript. *In Paket R1 durch das eigene Design ersetzt und entfernt.*
- **Browser-Besonderheiten in Tests:** Safari springt mit Tab nicht auf Links und fokussiert Buttons beim Klick nicht; die betreffenden Tastaturtests laufen daher nur in Chromium bzw. nutzen `focus()`.

## 6. Umsetzung Paket 8 (Entscheidungen)

- **Seiten:** „Aufgaben“ listet alle offenen Aufgaben in zwei Gruppen (wiederkehrend, einmalig), je nach Fälligkeit und Titel sortiert, als Karten mit Bearbeiten und Löschen. Neu: `#/aufgaben/neu` und `#/aufgaben/bearbeiten/<id>`; beide gehören in der Navigation zu „Aufgaben“ (`aria-current="true"`, die Seite selbst hat `"page"` nur bei den vier Hauptseiten). Eine Adresse zu einer unbekannten Aufgabe zeigt „Aufgabe nicht gefunden“. Erledigte einmalige Aufgaben stehen nicht in der Liste, sondern in „Erledigt“ (Paket 11).
- **Formular:** Feste Felder in dieser Reihenfolge: Art (nur beim Anlegen; später nicht änderbar), Titel, Rhythmus (Abstand und Einheit, nur wiederkehrend), Termin, Zuständig, Notiz. Der Termin ist beim Anlegen heute; „Zuständig“ ist mit „Ich bin“ vorbelegt (sichtbar und änderbar), damit niemand eine fremde Zuständigkeit übersieht, die man erst wählen müsste.
- **Prüfung (`checkTaskForm`, Fachlogik):** Titel getrimmt, nicht leer, höchstens 80 Zeichen; Notiz höchstens 500; Abstand ganze Zahl 1–365; Termin ein echter Tag zwischen 2000 und 2100 (verhindert Tippfehler und Überläufe der Datumsrechnung). Jede Meldung steht am Feld.
- **Barrierefreie Formulare:** Alle Felder entstehen aus `fields.tsx` (`TextField`, `TextAreaField`, `SelectField`, `RadioGroup`): sichtbares `<label>`/`<legend>`, Hinweis und Fehler direkt am Feld, `aria-describedby`, `aria-invalid`. Nach dem Absenden mit Fehlern landet der Fokus auf dem ersten fehlerhaften Feld (Reihenfolge `TASK_FORM_FIELD_ORDER`); die Meldung eines Feldes verschwindet, sobald man es ändert. Die Ersteinrichtung nutzt dieselben Bausteine.
- **Bearbeiten:** `updateTask` ändert Titel, Termin, Notiz, Rhythmus und feste Zuständigkeit. Eine geänderte feste Zuständigkeit beendet eine Übernahme „nur dieses Mal“ (F5); bleibt sie gleich, bleibt die Übernahme. Checkliste, Erledigungen und der erledigt-Zustand bleiben.
- **Löschen:** Immer über `DeleteTaskDialog` (native `<dialog>`, Fokus zuerst auf „Abbrechen“). Die Rückfrage nennt die Zahl der Einträge in „Erledigt“, die mit verschwinden. Entscheidung: Die Historie wird mit gelöscht (wie in ANFORDERUNGEN.md, F3 Löschen), weil ein Eintrag ohne Aufgabe weder angezeigt noch rückgängig gemacht werden kann; `parseAppData` lehnt verwaiste Erledigungen ohnehin ab. Löschen geht aus der Liste und aus dem Bearbeiten-Formular.
- **Rückmeldung:** Nach Anlegen, Speichern und Löschen steht auf „Aufgaben“ eine Meldung in einem Bereich mit `role="status"` (wird vorgelesen). Nach einem Löschen in der Liste, wo die Schaltfläche verschwindet, springt der Fokus auf die Überschrift.
- **Speicherfehler:** Schlägt das Speichern fehl, bleibt man im Formular, die Eingaben bleiben stehen und eine Meldung „Nicht gespeichert“ erscheint; beim Löschen „Nicht gelöscht“.
- **Schaltflächen in der Liste:** Sichtbarer Text „Bearbeiten“/„Löschen“, zugänglicher Name „Bearbeiten: Titel“ (`aria-label`; der Name beginnt mit dem sichtbaren Text). Text, der nur für Screenreader da ist, wäre in Chromium mit Leerzeichen eingefügt worden.
- **Tests:** E2E-Tests warten nach einem Seitenwechsel, bis die Überschrift den Fokus hat (`goToPage`, `expectPageShown` in `tests/e2e/helpers.ts`), bevor sie tippen oder Tasten drücken. Der Fokussprung läuft nach dem Zeichnen und nahm vorher in WebKit unter Last gelegentlich einem zu früh gestarteten Test den Fokus (ein bestehender Test war dadurch in etwa 5 % der Läufe rot).

## 7. Umsetzung Paket 9 (Entscheidungen)

- **Fachlogik `src/domain/week.ts`:** `weekView({ tasks, completions, shownDay, today, filter, person })` liefert `position` (`past | current | future`), sieben Tage (`days`, je mit `isToday` und `entries`) und `overdue`. Ein Eintrag ist `open` (mit `daysOverdue`) oder `done` (mit der Erledigung, daraus „erledigt von“). Reine Funktion, „heute“ und die gezeigte Woche kommen als Parameter.
- **Regeln:** Eine Aufgabe steht an ihrem Fälligkeitstag; wiederkehrende haben nur einen (den nächsten), also keine Vorschau. Überfälliges (Termin vor heute) steht nur in der **laufenden** Woche im Block „Überfällig“ (älteste zuerst) und nicht zusätzlich an seinem alten Tag; in vergangenen Wochen bleibt eine unerledigte Aufgabe an ihrem Tag und ist als überfällig markiert, künftige Wochen haben nichts Überfälliges. Erledigtes erscheint **nur in vergangenen Wochen**, und zwar an dem Tag, an dem die Aufgabe fällig war (`previousDueDate`), mit „Erledigt von … am …“; in der laufenden und in künftigen Wochen ist abgehakt = weg (F3). Innerhalb eines Tages stehen offene vor erledigten Einträgen, jeweils nach Titel.
- **Filter:** „Nur meine“ nutzt `isMine` (aktuelle Zuständigkeit samt Übernahme „nur dieses Mal“, „beide“ zählt für beide) auf die Aufgabe, auch bei erledigten Einträgen. Der Filter ist Zustand der Seite (nicht gespeichert) und beginnt mit „Alle Aufgaben“.
- **Abhaken und Rückgängig in den Daten:** `completeInData` und `undoInData` (`taskManagement.ts`) wenden `completeTask`/`undoCompletion` auf die gesamten App-Daten an. Die App (`App.tsx`) vergibt die Erledigungs-ID (`crypto.randomUUID()`), setzt „heute“ und „erledigt von“ = „Ich bin“ und speichert über `saveData`; schlägt das Speichern fehl, bleibt die Anzeige unverändert und die Seite zeigt „Nicht gespeichert“.
- **Seite `WeekPage`** (Aufbau in Paket R1 ersetzt, siehe Abschnitt 8): `h1` „Wochenübersicht“; darunter Wochenwechsel (Vorherige Woche / Diese Woche / Nächste Woche als Buttons in einer `nav`), Filter als `RadioGroup` („Anzeigen“), eine Zeile `role="status"` mit der gezeigten Woche („Diese Woche: …“, „Vergangene Woche vom …“, „Woche vom …“; wird beim Blättern vorgelesen). Überfällig und jeder Tag sind `section`s mit `h2` (Tage: „Mi, 21.10.2026 (heute)“, heute zusätzlich `aria-current="date"` und kräftiger Balken); leere Tage sagen „Keine Aufgaben.“. Die Woche ist ein Abstand in Wochen zur laufenden (nicht ein fester Tag), damit „diese Woche“ nach Mitternacht mitwandert.
- **Heute:** `useToday()` (`src/ui/useToday.ts`) prüft jede Minute und beim Wiedereinblenden des Tabs, ob der Tag gewechselt hat, sodass eine über Nacht offene Seite weiterrückt.
- **Hinweis nach dem Abhaken:** Ein `section`-Bereich „Hinweis“ mit Text („… ist abgehakt. Nächster Termin: …“ bzw. „… steht jetzt unter „Erledigt““) und der Schaltfläche „Rückgängig“ bekommt den Fokus (die gedrückte Schaltfläche ist verschwunden; so wird der Text vorgelesen und Tab führt zu „Rückgängig“ und zur nächsten Aufgabe). Bewusst keine `role="status"`, um doppelte Ansagen zu vermeiden, und kein Zeitablauf (WCAG 2.2.1). Es gibt nur den Hinweis zur zuletzt abgehakten Aufgabe; ältere Erledigungen macht man ab Paket 11 über „Erledigt“ rückgängig. Nach „Rückgängig“ erscheint eine Bestätigung ohne weitere Schaltfläche.
- **Kleinste Lösung statt späterer Pakete:** Ohne Aufgaben zeigt die Seite statt der Wochen nur „Es gibt noch keine Aufgaben.“ mit Link „Erste Aufgabe anlegen“. „Erledigt“ bleibt Platzhalter bis Paket 11. - **Fachlogik bleibt rein.** `src/domain/` ändert sich nur für das Datenmodell v3 (`schemaVersion` 3: Erledigung bekommt `completedAt` und `assigneeAtCompletion`; Migration v2 → v3 lässt beide weg) und für die Statistik (`statistics.ts`, E2-4b). Die Domänenfunktionen geben weiter ganze `AppData` zurück.
- **Lokal zuerst, Server als Abgleich.** Jedes Gerät hält eine Kopie der Haushaltsdaten und eine Warteschlange ausstehender Änderungen (`outbox`). Anzeigen und Speichern gehen immer sofort lokal. Der Abgleich (`sync`) schickt die Warteschlange der Reihe nach und holt dann alles, was sich seit dem letzten Stand geändert hat. Echtzeit-Ereignisse stoßen nur einen Abruf an; abgerufen wird auch beim Start, bei `online` und beim Wiedereinblenden.
- **Neue Schichten:** `src/sync/` (`changes.ts`, `merge.ts`, `outbox.ts`, `syncedStorage.ts`, `remote.ts`, `fakeRemote.ts`, `supabaseRemote.ts`; Abdeckung ≥ 90 %), `src/auth/` (Schnittstelle `Auth`, Umsetzungen Supabase und Fake), `src/backend.ts` (Modus `supabase` | `fake` | `local`), `supabase/` (Konfiguration und Migrationen), `scripts/fake-server.ts`. `AppStorage` bekommt `subscribe(listener)` und `syncStatus`; `load`/`save` bleiben.
- **Modi:** `supabase` für die echte App, `fake` für die E2E-Tests, `local` für `npm run demo` und für die Online-Version bis zum Ende von E2-3 (Build-Schalter `VITE_BACKEND`).
- **Konfliktregeln:** Pro Feld gewinnt die zuletzt beim Server angekommene Änderung (Serverzeit), die Checkliste zählt als ein Feld; gleichzeitiges Abhaken desselben Durchgangs zählt einmal; Löschen gewinnt gegen Bearbeiten; Rückgängig nur für die letzte Erledigung einer Aufgabe auf dem Server.
- **Sicherheit:** Row Level Security auf jeder Tabelle, Schreiben nur über Datenbankfunktionen, `anon` ohne Rechte; Projekt-URL und Publishable Key (öffentlich) per `VITE_SUPABASE_URL`/`VITE_SUPABASE_PUBLISHABLE_KEY` in den Build; Content Security Policy als `<meta>`; der Service Worker fasst nur eigene Adressen an; der Einladungstoken steht im Hash.

## E2.4 Umsetzung Paket E2-0 (Entscheidungen)

Für Nutzer ändert sich nichts: Online-Version und Demo laufen weiter im Modus `local`; der Produktions-Build enthält keinen Code des gemeinsamen Speichers (geprüft: keine Fundstelle von `kruemel:sync`, `FakeHousehold` in `dist/assets`; der Hauptbündel wuchs nur um 1 kB durch die Anpassungen in `App.tsx`). Keine neue Abhängigkeit.

**Datenmodell v3.**
- `SCHEMA_VERSION` = 3. Eine Erledigung hat optional `completedAt` (ISO 8601, UTC, wie `toISOString` es schreibt) und `assigneeAtCompletion` (`personA | personB | both`). Fehlt ein Feld, heißt das „unbekannt“; es wird nie geraten.
- `assigneeAtCompletion` ist die **feste** Zuständigkeit der Aufgabe, nicht eine einmalige Übernahme (`takenOverBy`). Nur so lässt sich „füreinander übernommen“ später zählen: Übernimmt Robin eine Aufgabe von Alex nur dieses Mal, steht Alex als Zuständiger und Robin als Erledigender da. Bei dauerhafter Übernahme ändert sich die feste Zuständigkeit, dann zählt es nicht mehr als „füreinander“.
- `completeTask` setzt `assigneeAtCompletion` immer; `completedAt` kommt als Parameter (`CompleteInput.completedAt`), weil die Fachlogik keine Uhr kennt. `App.tsx` übergibt `new Date().toISOString()`. Die Demo-Daten setzen kein `completedAt` (die Uhrzeit in „Heute“ ist Sache von E2-4).
- `migrate.ts`: Schritt 2 → 3 hebt nur die Version an; Daten der Version 1 laufen durch beide Schritte. `validate.ts` prüft beide Felder einzeln mit Fundstelle. Getestet für Laden (`localStorage.test.ts`, `outbox.test.ts`) und Import (`exportImport.test.ts`), Fixtures `asVersion2`/`withoutVersion3Fields`.

**Änderungen statt ganzer Daten (`src/sync/changes.ts`).**
- `AppStorage.save(data)` bekommt weiter ganze `AppData`. `diffData(vorher, nachher)` leitet daraus `Change`-Einträge ab: `setNames`, `saveTask` (Felder-Patch `{set, unset}`; neue Aufgabe mit `create` und allen Feldern), `deleteTask`, `complete` (Erledigung plus Patch der Aufgabe), `undo` (Erledigung zurücknehmen plus Patch), `replaceAll`. Eine Erledigung trägt die Änderung ihrer Aufgabe mit, damit der Server beides in einem Schritt macht.
- `applyChange(daten, änderung, gelöschteAufgaben)` führt eine Änderung aus und sagt, ob der Server sie annehmen würde (`PushResult`: `applied` oder `rejected` mit Grund `alreadyDone` (mit `by`), `taskGone`, `notLast`, `completionGone`). **Dieselbe Funktion** nutzen das Gerät (eigene Änderungen sofort zeigen) und der Fake-Server, damit beide dieselben Regeln haben. Die Konfliktregeln aus `ETAPPE2-PLAN.md` Abschnitt 1 stehen damit an einer Stelle und sind darin getestet („Konflikt: …“ in `changes.test.ts`, `remote.contract.ts`, `syncedStorage.test.ts`).
- „Zuletzt angekommen gewinnt“ ergibt sich daraus, dass der Server die Patches in der Reihenfolge ihrer Ankunft auf den Stand legt; die Geräteuhr spielt keine Rolle.

**Schichten.**
- `Remote` (`remote.ts`): `pull(cursor)` → geänderte Zeilen (auch Grabsteine) und neuer Stand (opak), `push(change)`, `subscribe(hint)`. Ein Fehler der Verbindung ist ein `RemoteError`.
- `FakeHousehold` (`fakeHousehold.ts`): der Server eines Haushalts im Speicher. Zählt jede Änderung der Daten hoch (`clock`, die „Serverzeit“), führt Grabsteine für gelöschte Aufgaben und Erledigungen und erkennt eine zweimal zugestellte Änderung an ihrer `id` (gibt dieselbe Antwort). `FakeRemote` (`fakeRemote.ts`) hängt davor, mit Schaltern `online` und `loseNextAnswer` (Antwort geht verloren) für Tests. `FakeServer` (`fakeServer.ts`) verwaltet mehrere Haushalte und die Geheimnisse der Personen und beantwortet die HTTP-Aufrufe; `FakeHttpRemote` spricht ihn über `fetch` und `EventSource` an.
- `SyncedStorage` (`syncedStorage.ts`, `outbox.ts`, `merge.ts`, `locks.ts`, `triggers.ts`): Die lokale Kopie (`base`, zuletzt vom Server geholt), der Abrufstand und die Warteschlange liegen **in einem Eintrag** `kruemel:sync` im `localStorage`. Angezeigt wird `viewOf(base, outbox)`. Der Abgleich sendet die Warteschlange der Reihe nach, holt dann Änderungen (`mergeDelta` ist idempotent, überlappende Abrufe schaden nicht) und meldet abgelehnte Änderungen als `conflict`-Ereignis. Er läuft beim Start, nach jedem Speichern, bei Hinweisen des Servers, bei `online` und wenn die App wieder sichtbar wird (`browserTriggers`).
- **Sperren:** Jedes Lesen-und-Schreiben des Eintrags geschieht unter der Sperre `kruemel-sync-state`, der ganze Abgleich unter `kruemel-sync-run` (nur ein Tab sendet; ein zweiter überspringt, weil der erste die gemeinsame Warteschlange mit abarbeitet). Web Locks wenn vorhanden, sonst eine Sperre im Tab (`browserLocker`).
- **Basis für `save`:** Es vergleicht mit dem, was die App zuletzt bekommen hat (`load`, `save`-Ergebnis oder `data`-Ereignis), nicht mit dem aktuellen Stand der Kopie. Eine Änderung des anderen Geräts, die die App schon zeigt, wird so nie als „von dieser App gelöscht“ gedeutet.

**Änderungen an `AppStorage` und `App.tsx`.**
- `AppStorage.save` gibt die anzuzeigenden Daten zurück (bei `local` die übergebenen, beim gemeinsamen Speicher zusätzlich, was aus der Warteschlange eines anderen Tabs dazukam). Neu: `subscribe(listener)` mit `StorageUpdate` (`data`, `status`, `conflict`) und `syncStatus()` (`synced | syncing | offline | unreachable`). `createLocalStorage` meldet nie etwas und ist immer „synced“.
- `App.tsx` zeigt `data`-Ereignisse ohne Neuladen. Alle Handler lesen den neuesten Zustand aus einer `useRef` (`latest`) statt aus dem Zustand der letzten Darstellung und setzen den Zustand danach funktional, damit eine Änderung des anderen Geräts, die zwischen zwei Darstellungen ankommt, nicht überschrieben wird. Anzeige von Abgleichsstand und Konflikt-Hinweisen: E2-3.

**`src/auth/`.** Schnittstelle `Auth` (`session`, `requestCode`, `verifyCode`, `signOut`, `onChange`), Fehler `AuthError` mit `failure` (`invalidEmail | wrongCode | expiredCode | tooManyTries`). `FakeAuth` im Speicher mit den Regeln des echten Dienstes: sechs Ziffern, 10 Minuten gültig, nur einmal, nach fünf falschen Versuchen verbraucht, ein neuer Code macht den alten ungültig; `lastCode` ersetzt die E-Mail. Die HTTP-Fassung für den Fake-Server kommt mit E2-2, zusammen mit der Oberfläche.

**`src/backend.ts` und Build.** `backendMode(buildModus, VITE_BACKEND)` wählt `local`, `fake` oder `supabase` (Standard: `e2e` → `fake`, sonst `local`; unbekannte Werte brechen den Build ab). `vite.config.ts` macht daraus die Konstante `__BACKEND__`; `main.tsx` verzweigt darauf, sodass der Code der anderen Modi nicht im Build steht. `supabase` wirft bis E2-3 einen Fehler. `__FAKE_SERVER__` (Standard `http://localhost:4180`, `FAKE_SERVER_URL`) nennt dem Test-Build den Fake-Server. `src/sync/browserFake.ts` (nur für `e2e`, nicht in der Abdeckung) liest das Geheimnis der Person aus `kruemel-fake:session` im Browser-Speicher, solange es keine Anmeldeseite gibt.

**Fake-Server für die E2E-Tests (Abweichung vom Plan).** Der Plan sah ein Skript vor, das Node per Type-Stripping startet. Die Quelldateien importieren sich aber ohne Dateiendung (`../domain/task`), das kann Node nicht auflösen. Deshalb baut `vite build --ssr scripts/fake-server.ts --outDir dist-fake` das Skript zu einer Datei, die Playwright mit `node dist-fake/fake-server.js` startet (Port 4180, `GET /health` als Bereitschaftsprüfung, Server-Sent Events unter `/events`, offenes CORS, nur für Tests). Die App im Modus `e2e` baut `vite build --mode e2e --outDir dist-e2e` (Port 4175, ohne Service Worker). Beides erledigt `npm run build:e2e`; `npm run check` hat dafür zwei eigene Schritte (5 und 6 von 7, siehe `scripts/check.mjs`). Das `serviceWorker()`-Plugin überspringt den SSR-Build. Statt `@types/node` gibt es `scripts/node-http.d.ts` mit dem einen Modul, das das Skript braucht (N7); `tsconfig.json` erlaubt `.ts`-Endungen in Importen (`vite.config.ts` importiert `src/backend.ts` so, damit Vite die Konfiguration ohne Warnung lädt).
